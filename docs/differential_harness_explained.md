# How the differential harness works

The harness is the bond between the **Lean reference model** and the
**implementation**. It never translates one into the other. It asks both the
same question thousands of times and compares the answers. That is the whole
idea, and it is why the implementation may be Python, Rust, or anything else.

Source: `tracelean/core/src/drt/` — `bind.rs` `config.rs` `gen.rs` `infer.rs`
`lean_runner.rs` `protocol.rs` `run.rs` `schema.rs`.
Worked example: `example/formal/Checkout.lean`, `example/engine/pricing.py`,
`example/.tracelean/drt.json`. There is no harness directory: that is the point.

---

## 1. Two long-lived processes, one line-delimited JSON protocol

Neither side is linked into TraceLean. Each is a **subprocess** that reads one
JSON case per line on stdin and writes one JSON reply per line on stdout.

```
                    ┌─────────── TraceLean (drt::run) ───────────┐
                    │  generate case  →  ask both  →  compare    │
                    └──────┬──────────────────────────────┬──────┘
         {"case":7,"op":"REQ-CHECKOUT.total","input":…}   │
                           ▼                              ▼
              drtRunner (compiled Lean)      tracelean_drt_runner.py
                  generated by TraceLean        shipped with TraceLean
              {"case":7,"output":{…}}            {"case":7,"output":{…}}
```

Neither side is written by the project. Both are TraceLean's code, driven by the
bindings in `.tracelean/drt.json`.

Case and reply shapes live in `protocol.rs`:

```rust
pub struct Case  { case: u64, op: String, input: Value }
pub struct Reply { case: u64, output: Option<Value>, error: Option<String> }
```

Why subprocesses and not a library call: the model is Lean and the code may be
anything, so the only interface both can honour is bytes on a pipe. Why
long-lived: a run executes thousands of cases; starting an interpreter or a
binary per case would dominate the wall-clock.

Two consequences, which the shipped runners already handle and which a
hand-written adapter has to get right:

- **Flush after every reply.** A pipe is block-buffered. Without the flush the
  comparator waits for a reply that is sitting in the runner's buffer, and the
  run deadlocks.
- **A crash is an answer, not an abort.** Exceptions become
  `{"case":n,"error":"ValueError: …"}`. The model may also fail on that input —
  *both fail* is agreement, *one fails* is a real divergence. A runner that dies
  on a bad input destroys the run instead of reporting it.

`Runner::ask` has a per-case timeout and `Runner::restart` a restart budget;
timeouts and restarts are recorded in `DrtResult.incidents`, separately from
divergences, because a hung process is not evidence of a behaviour difference.

## 2. The Lean side is generated, not written

You do not write the Lean runner. `lean_runner.rs` generates a `Main.lean` into
`.tracelean/drt/`, with a `lakefile` that `require`s your model package, and
`lake build` produces `.tracelean/drt/.lake/build/bin/drtRunner` — the `cmd` you
see in `drt.json`. The generated source is:

```lean
structure Case where case : Nat; op : String; input : Json  deriving FromJson, ToJson

def handle (c : Case) : Except String Json :=
  <dispatch generated from the bindings>

partial def loop … -- read a line, handle, write the reply, repeat
```

The dispatch is a `match` on `c.op` that decodes `c.input` and calls your model
function. Two details that were subtle enough to be worth naming:

- **Module names are relative to the lake package root**, not the project root,
  and the `require` must use the package's *declared* name (`lakefile.toml`'s
  `name =`), not its directory name. Getting that wrong does not merely fail —
  Lake 4.12 **deletes the required directory**. `check_requires()` now refuses
  to run `lake build` on a mismatch.
- If the model function takes **one structure argument**, the input is decoded
  whole (`fromJson? (α := Order) c.input`) rather than field by field.

## 3. The implementation side is called directly — no adapter

This is where TraceLean changed after looking at how Cedar does it.

The first version generated one Python file per binding under `harness/`. Six
bindings produced six files that differed in about six lines each and shared
fifty lines of identical protocol boilerplate: the stdin loop, the JSON encode
and decode, the flush, the exception handler. That is duplication wearing a
generator's clothes, and it made every new binding cost a file.

Cedar does not work that way. `cedar-spec` has **one** DRT harness for the whole
system. The Lean side exposes a small fixed API through `cedar-lean-ffi`, input
generation lives once in `cedar-policy-generators` (type-directed `Arbitrary`
instances for schemas, entities, policies, requests), and each of the 30-plus
fuzz targets is a short declaration of *what to generate and what to compare* —
`abac`, `rbac`, `validation-drt`, `tpe-is-authorized-drt` and the rest. The
mechanism is written once; the per-target part is small.

So TraceLean ships the mechanism too. `core/src/drt/runners/python_runner.py` is
embedded in the binary, written into `.tracelean/drt/` when a run starts, and
driven by the binding:

```json
"implementation": {
  "language": "python",
  "entry": "engine/pricing.py::price",
  "params": { "subtotalCents": "subtotal_cents" }
}
```

`entry` is a *path*, not a module name, because this project has no import
conventions to rely on — the implementation may live anywhere. `params` records
the places where the two sides spell the same argument differently, which is the
one genuinely project-specific fact in the whole binding. One runner process
serves every Python binding and dispatches on `op`, mirroring the Lean runner.

The runner also unwraps dataclasses, named tuples and plain objects into the
shape Lean's `deriving ToJson` produces, so the common return types need no help.

**There is no escape hatch, on purpose.** An earlier version kept a
`{"cmd": [...]}` form for a hand-written adapter. The argument against it is not
that it was duplication — it is that an adapter is an *untrusted participant in
the comparison it exists to enable*. Arbitrary code between the implementation
and the comparator can make a divergence disappear, and that is the one place in
this system where hiding one would be both easy and invisible. A binding
describes a call and stops there, so the only project code that runs is the
implementation's own.

The narrow, declared exception is `convert`: a named function in the project,
pointed at from the binding, for a return value the runner cannot reshape. It is
visible in `drt.json` where a reviewer reads it, rather than buried in a file
that looks like plumbing.

Rust implementations have no runner yet, and `bind.rs` says so rather than
emitting a template that has never been run end to end. A compiled language needs
a *generated* dispatching runner, the way the Lean side already works.

## 3b. What we still do not do that Cedar does

Worth naming rather than glossing over:

- **Coverage-guided fuzzing.** Cedar runs under `cargo fuzz` / libFuzzer, so the
  generator is steered by coverage feedback. TraceLean draws from a seeded PRNG
  with boundary edges mixed in — better than uniform random, blind compared to
  libFuzzer.
- **Type-directed generators for user datatypes.** Cedar hand-writes `Arbitrary`
  instances that produce *well-formed* policies and entities. TraceLean infers a
  schema from the model's signature, which covers scalars and records and does
  not yet cover a datatype with an invariant.
- **In-process FFI.** Cedar calls Lean through FFI; TraceLean uses pipes between
  two processes. Pipes are the reason the implementation can be in any language,
  and the cost is throughput.

## 4. Where the inputs come from

`infer.rs` reads the **model's** signature and derives a `Schema` (`schema.rs`)
— `nat`, `bool`, `struct`, sum types with named constructors. `gen.rs` draws
from it with a seeded PRNG, so a run is reproducible from `(seed, cases)`.

One correction worth understanding, because it is the difference between a real
test and theatre: an unbounded `Nat` drawn uniformly from the whole 32-bit range
essentially never lands near a threshold. A model branching at 5000 and 20000
would have every case fall in the top branch, report "2000 cases, no
divergences", and have established nothing. `infer::boundaries()` now scans the
model source for numeric literals and adds **every literal ±1** to the schema as
`edges`, which the generator mixes into its draws. Proven by mutation: the same
injected bug produced 0 divergences without edges and 32/2000 with them.

Seeds that once found a divergence are appended to `.tracelean/drt/seeds/` and
replayed first on later runs, so a fixed bug stays fixed.

## 5. Comparison, shrinking, triage

`replies_agree` compares the two replies structurally. On a disagreement the
input is **shrunk** (`gen::shrink`) — repeatedly simplified while the
disagreement persists — so what you are shown is the smallest input that still
diverges, not the random 9-digit one that happened to hit it.

Then `Triage`, which is deliberately a decision and not an assumption:

```rust
enum Triage { Untriaged, ImplBug, ModelBug, AdapterBug }
```

The model is *not* privileged. It was written from the requirement by a human or
an LLM and is exactly as capable of being wrong as the code, so a divergence
means "these two disagree", and a person says which one is wrong.

## 6. What a green run is actually worth

A case count alone is theatre. `Coverage` records which **input constructors**
were exercised and which **output variants** were observed, and a run must clear
a `CoverageFloor` (default: every declared input constructor exercised and at
least one output variant seen).

```rust
pub fn earns_l3(&self) -> bool {
    self.divergences.is_empty() && self.coverage_floor_met && self.cases_run > 0
}
```

This is falsification, not proof — which is precisely why a clean run earns
**L3** and not L4. L4 is for a machine-checked proof about the model. A run that
found nothing is evidence that the bug is not in the region you sampled; it is
not a guarantee that there is no bug.

## The example, end to end

`REQ-CHECKOUT.total` in `example/product/checkout.md`, modelled by
`Checkout.price` in `example/formal/Checkout.lean`, implemented by
`pricing.price` in `example/engine/pricing.py`, bound by one JSON object in
`example/.tracelean/drt.json`. Six bindings, 2000 cases each, zero divergences,
and **no harness code in the project at all**. `make e2e` builds the Lean runner
and runs all six.
