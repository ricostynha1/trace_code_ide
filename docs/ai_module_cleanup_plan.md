# AI module cleanup plan

Source: a manual code review of `core/src/ai/` (paths below are relative to
[`tracelean/`](../tracelean/), not this `docs/` folder). This is a distinct,
larger pass than [`new_features_work_plan.md`](new_features_work_plan.md) item
1 (which is now implemented — schema-driven arg validation via
`tool_errors::validate_args`); this doc covers what's left: dead code, three
separate hardcoded tool catalogs that have drifted out of sync with each
other, provider-specific parsing that should be shared, and a Mock provider
that's more machinery than it needs now that the project is stable.

Every finding below was verified against the current tree (not assumed from
memory) — file, line, and caller counts are as of 2026-07-21.

---

## 1. Delete `bedrock_pricing.rs` — redundant hand-maintained pricing table

**Current state:** `ai/bedrock_pricing.rs` is an 88-line hardcoded
`match model_id { ... }` returning `(input_cost, output_cost)` for ~40 Bedrock
model IDs, headed by a comment "Last updated: 2026-07-09 — Update this file
when AWS changes pricing." Its only caller is `bedrock.rs::model_for_id`
(line 972). Meanwhile `data/models.json` — embedded at compile time via
`include_str!` in `model_catalog.rs:52` — already contains pricing for every
one of those same model IDs (confirmed: `anthropic.claude-sonnet-5`,
`minimax.minimax-m2.5`, etc. all present), generated by
`scripts/generate_models.py` from LiteLLM + provider cache config. Two sources
of truth for the same numbers, one of them a manually-edited Rust match
statement that will silently drift (exactly the kind of bug `bugs.md`
already recorded once: "MiniMax's cached price stayed wrong after the
pricing table was fixed").

**Fix:** Delete `bedrock_pricing.rs`. Change `bedrock.rs::model_for_id` to
look up pricing from the embedded model catalog (`model_catalog.rs` already
exposes catalog entries keyed by model id for the "enrichment" pass at
`model_catalog.rs:154-161` — reuse that lookup, or expose a small
`model_catalog::pricing_for(model_id) -> Option<(f64, f64)>` if no such
accessor exists yet) instead of `bedrock_pricing(model_id)`. Keep the
`(0.0, 0.0)` fallback for genuinely unknown IDs.

**Risk:** low, purely a data-source swap; `model_for_id` is exercised by
existing tests that assert on specific models' costs — rerun those after the
change to confirm the catalog and the deleted table agreed on every model
that had a test.

## 2. Move Bedrock's tool-dialect parsing/rendering into a shared, reusable module

**Current state:** `bedrock.rs` (1549 lines) contains, alongside the
provider's actual HTTP logic, all of the text-based tool-calling dialect
handling: `render_tools_as_text` (line 65, renders schemas into the
`<tools>...</tools>` system-prompt block per `ToolCallFormat`),
`parse_hermes_blocks`/`parse_mistral_prefix`/`parse_json_body`/
`parse_minimax_native` (lines 206-546, parse `<tool_call>`,
`<minimax:tool_call>`, `[TOOL_CALLS]` etc. out of model text), and
`strip_tool_blocks` (line 546, strips those same blocks back out of
displayed content). This is genuinely provider-*model* logic, not
provider-*transport* logic: it only matters for `ToolPassing::SystemPromptEmbed`
models (Bedrock+MiniMax today), and the same need could hit any other
provider that routes to a model without native tool-call support —
`openrouter.rs` (489 lines) currently has zero of this code because every
model routed through it today happens to support native tool calling, not
because OpenRouter structurally can't need it.

One piece is *already* properly centralized and needs no change: dialect
*error-message* rendering (`format_tool_call_error`, `render_tool_call`) live
in `tool_errors.rs` and `bedrock.rs` already calls into them (lines 839,
1078, 1382) rather than duplicating that logic locally. Good — don't touch
this part.

**Fix:** Extract `render_tools_as_text`, the four `parse_*` functions, and
`strip_tool_blocks` into a new module, e.g. `ai/tool_dialects.rs` (or
`ai/model_specific_prompt_construction.rs` if that name is preferred),
parameterized purely by `ToolCallFormat` — no Bedrock-specific state. Update
`bedrock.rs` to call into it. This gives `openrouter.rs` (or any future
provider) the same dialect support for free the day a `SystemPromptEmbed`
model gets routed through it, instead of that logic needing to be
re-invented or copy-pasted.

**Risk:** low — this is a pure code move (same function bodies, same tests
follow them), not a behavior change. Bedrock's existing dialect tests
(`sample_tools`, the `HermesJson`/`MiniMaxXml` render tests at lines
1274-1290) move with the functions.

## 3. Retire the second hardcoded tool catalog (`tools.rs::builtin_tool_definitions`)

**Current state:** There are now confirmed to be **two independent, hand-written
tool catalogs** in this codebase:

- `data/tools.json` — the documented single source of truth (per
  `docs/TOOL_SINGLE_SOURCE.md`), loaded by `ToolRegistry`, actually used by
  `tool_executor.rs`'s dispatch and by the live agent runtime. Canonical
  static tool names: `discover_tools`, `list_directory`, `find`, `read_file`,
  `edit_file`, `replace_str`, `run_shell`, `web_search`, `web_fetch`,
  `help_tool` (+ 5 dynamic: `delete_file`, `query_trace_graph`,
  `query_code_element`, `list_requirements`, `get_symbols`).
- `tools.rs::builtin_tool_definitions()` (line 145) — a **second**,
  completely independent hardcoded `Vec<ToolDefinition>` with tool names that
  **do not exist** in `data/tools.json` or in `tool_executor.rs`'s dispatch
  table at all: `count_lines`, `read_range`, `write_range`, `str_replace`,
  `list_files`, `find_grep`, `find_embed`. (`str_replace`, `list_files`,
  `find_grep`, `find_embed` are at least still routed as dispatch aliases in
  `tool_executor.rs`; `count_lines`, `read_range`, `write_range` are not
  handled anywhere in the dispatch `match` — calling them returns "Unknown
  tool".)

This second catalog isn't dead: it's used by `tools_as_system_prompt()`
(tools.rs:418) which builds prompts for `agents.rs`'s four standalone agents
(Elicitation/Formalisation/Implementation/Repair — see finding 9), **and** by
`mcp_host.rs::handle_tools_list` (line 110), which is live and reachable —
any external MCP client connecting to TraceLean via
`gui_backend/src/ipc/mcp_commands.rs` gets served this stale tool list over
JSON-RPC and would call tools like `read_range`/`write_range` that silently
fail with "Unknown tool" today. That's a real, currently-shipping bug, not
just tech debt.

Related dead code found in the same area: `tools.rs::tool_calling_rules()`
(line 480) has **zero callers anywhere in the codebase** — confirmed by grep.
Delete it outright.

**Fix:**
1. Delete `tool_calling_rules()` — no callers, no risk.
2. Replace `builtin_tool_definitions()`'s hardcoded `Vec<ToolDefinition>`
   with a function that derives the same shape from `ToolRegistry`
   (`registry.all_tool_entries()` already returns everything needed: name,
   description, schema, example). This makes `mcp_host.rs` and `agents.rs`
   automatically track `data/tools.json` instead of a second, independently
   maintained list — fixes the MCP stale-tool-name bug as a side effect of
   removing the duplication, not as a separate patch.
3. Once `builtin_tool_definitions()` sources from `ToolRegistry`,
   `tools_as_system_prompt()` (tools.rs:418) can likely be replaced entirely
   by whatever prompt-building path the live agent runtime already uses for
   the real tool set — check `agent/runtime.rs`/`ai/mod.rs`'s `SYSTEM_PROMPT`
   construction before deciding whether `tools_as_system_prompt` survives as
   a thin wrapper or gets deleted too (depends on finding 9's outcome, since
   `agents.rs` is its only caller).

**Risk:** medium — touches the one live external-facing surface
(`mcp_host.rs`) that isn't covered by existing integration tests as far as
grep showed; add a test asserting `handle_tools_list`'s output names are a
subset of `ToolRegistry::static_tool_names()`/dynamic names before/after.
Add tests for that as well so

## 4. Move `tool_selector.rs`'s hardcoded enrichment/keywords into `data/tools.json`

**Current state:** `tool_selector.rs` has two more hand-maintained, per-tool
hardcoded tables that duplicate/extend `data/tools.json` content in Rust
instead of JSON:

- `get_enrichment(tool_name)` (line 46) — a `match` returning
  `category`/`aliases`/`examples` per tool name, used twice (lines 128, 198)
  to boost tool-discovery scoring.
- `category_boost(category, query_tokens)` (line 375) — a hardcoded
  `&[(&str, &[&str])]` mapping each category (`filesystem`, `editing`,
  `search`, `shell`, `traceability`, `requirements`, `code_analysis`,
  `commands`) to keyword lists, used twice (lines 261, 345).

Both are exactly the kind of per-tool metadata `data/tools.json` already
carries some of (`category`, `short_help`, `example`) — `aliases` and
scoring keywords are a natural extension of the same schema, not a
different concern.

**Fix:** Add `aliases: [String]` and `examples: [String]` fields to each
tool entry in `data/tools.json` (mirroring `get_enrichment`'s content
verbatim as the migration), and a top-level `category_keywords: {category:
[String]}` map (mirroring `category_boost`'s table). Change
`ToolJsonEntry`/`ToolsConfig` (`tool_registry.rs:35,65`) to deserialize the
new fields, and change `tool_selector.rs` to read them off the registry
instead of the two hardcoded functions. Delete `get_enrichment` and
`category_boost` once nothing calls them.

**Risk:** low — purely additive schema fields plus a mechanical read-path
swap; `tool_selector.rs` already has a test module (discovery ranking tests)
that will catch a scoring regression if the migrated data doesn't match.

## 5. Per-parameter error hints in `data/tools.json`

**Current state:** `tool_errors::format_arg_validation_error` (tool_errors.rs:206)
already builds validation-failure messages from `short_help`/`example` — this
is the middleware `TOOL_SINGLE_SOURCE.md` proposed and it's live. What it
doesn't yet do is let an individual *parameter* carry a custom hint for why
it commonly gets it wrong (e.g. `old_str` in `replace_str` needing to match
byte-for-byte, or a path parameter needing to be project-relative) — today
every wrong-type/missing-param message is generated from the same generic
template regardless of which parameter failed.

**Fix:** Add an optional `error_hint` string to each parameter's schema entry
in `data/tools.json` (`input_schema.properties.<param>.error_hint` — outside
standard JSON-Schema keywords, so harmless to the model-facing schema, read
only by our own validator). In `tool_errors::validate_args`, when a specific
parameter fails (missing or wrong type), look up that parameter's
`error_hint` in the schema and append it to the returned error string if
present; fall back to today's generic message otherwise. This is additive —
no existing behavior changes for tools that don't set the field.

**Risk:** low. Add a test mirroring
`arg_validation_error_pulls_usage_and_example_from_registry` but asserting
the hint text surfaces when present.

`tools.rs::tool_calling_rules()` (finding 3). The "PARALLEL / PRIORITY /

   actually still needed for `NativeParam` models (where the provider's own

## 8. Simplify the Mock provider — test-only, not a user-facing option

**Current state:** `MockProvider` (`mock.rs`) is a fully general interactive
provider: it queues each request (`Arc<Mutex<Vec<MockPendingRequest>>>`),
notifies the UI via an `mpsc` channel, and waits on a `oneshot::channel` (10
min timeout) for a human to paste back a JSON/text response through
`submit_response`. It is wired all the way into the GUI as a real,
user-selectable provider: `AiChatPanel.tsx:1073` has
`<option value="mock">Mock (Debug)</option>` in the same dropdown as
Bedrock/OpenRouter, plus a full polling/prompt-window UI
(`MockPromptWindow.tsx`, `mockPending`/`mockResponse` state, a
`get_mock_pending`/`mock_submit_response` IPC round-trip in
`AiChatPanel.tsx`). Separately, there's already a **second**, much simpler
mock path used only by automated tests: the `TRACELEAN_MOCK_AUTO` env var
(`mock.rs:187`) bypasses the whole interactive queue and returns a fixed
string — used today by `agent/runtime.rs`'s compaction tests and
`tui/tests/smoke.rs`.

Per the user: this project has stabilized enough that the interactive
paste-back workflow is no longer needed day-to-day, and the Mock provider
should stop being a clickable GUI option entirely — it should exist only for
tests, with real functions to script an expected response sequence (not a
single global env-var string).

**Fix:**
1. Remove `"mock"` from the GUI provider dropdown (`AiChatPanel.tsx:1073`)
   and delete the associated polling/prompt-window UI
   (`MockPromptWindow.tsx`, the `mockPending`/`mockResponse` state and
   `get_mock_pending`/`mock_submit_response` IPC calls in `AiChatPanel.tsx`,
   and the corresponding Tauri commands in `gui_backend` if they have no
   other caller). Keep `mock`/`ProviderKind::Mock` selectable from
   `tracelean-bench`'s `-p mock` CLI flag and from Rust tests — those are
   legitimate non-interactive callers, not the GUI.
2. Replace the interactive queue/channel/mutex machinery with a small
   test-oriented API: e.g. `MockProvider::with_responses(Vec<MockResponse>)`
   or a `.push_response(...)`/`.expect_call(...)` builder that returns
   queued responses in order (falling back to `TRACELEAN_MOCK_AUTO`-style
   single-string behavior for the simplest tests). This directly enables
   "particular functions to set the answer back" instead of only a single
   global env-var string, and removes the need for `mpsc`/`oneshot`/10-minute
   timeout/UI-polling entirely once nothing waits on a human — a real
   simplification of the async surface, not just a UI change.
3. Update the handful of existing tests that rely on `TRACELEAN_MOCK_AUTO`
   (`agent/runtime.rs` x3, `tui/tests/smoke.rs`) to the new API, or keep the
   env var as a thin compatibility path implemented in terms of the new
   builder if migrating every call site isn't warranted in the same pass.

**Risk:** medium — this removes a GUI-reachable path some workflow might
still depend on; confirm with the user before deleting
`MockPromptWindow.tsx`/the dropdown option outright, since "not clickable at
all" is an explicit product decision, not just a refactor.

## 9. Decide the fate of `agents.rs` / `response_parser.rs` (currently unreachable from the UI)

**Current state:** `agents.rs` (the Elicitation/Formalisation/Implementation/
Repair "standalone agents" — `docs/architecture.md:177` documents them as
built-in) is the **only** caller of `response_parser.rs` (4 call sites) and
of `tools::builtin_tool_definitions()`/`tools_as_system_prompt()` (findings
3/6). Its four Tauri commands (`run_agent_elicitation`,
`run_agent_formalisation`, `run_agent_implementation`, `run_agent_repair`)
are registered in `gui_backend/src/lib.rs:283-286`, so they're
callable — but a full grep of `react_frontend/` for `run_agent_`,
`elicitation`, `formalisation` found **zero** references anywhere in the
frontend. There is no button, no menu entry, nothing that invokes them.
This looks like a feature that was wired backend-first and never connected
to the UI, not something actively used.

This matters for sequencing: findings 3 and 6 both change based on whether
this code stays.

**Fix:** Not a code change by itself — a decision needed before findings 3/6
can be finished:
- **If it should be wired up:** add the missing frontend entry points (menu
  item / panel triggering `run_agent_*`), and then `agents.rs`'s tool-catalog
  and prompt dependencies get migrated onto the real `ToolRegistry`-backed
  path per findings 3/6 rather than deleted.
- **If it's abandoned/superseded** (e.g. the main chat-driven agent loop in
  `agent/runtime.rs` now covers what these four were meant to do):
  remove `agents.rs`, `response_parser.rs`, the four IPC commands and their
  `lib.rs` registrations, and `AgentResult`/related frontend TS types if any
  exist unused. This also resolves findings 3/6's last dependency for free.
  (It is ablsuouted superseded so they shold be removed)

**Risk:** none either way from a code-safety standpoint (it's an isolated,
disconnected subsystem) — the only risk is guessing wrong about intent,
which is why this is flagged as a decision point rather than pre-judged.

## Suggested execution order

Roughly cheapest/lowest-risk and most-isolated first, with the one true
blocking dependency (finding 9 gates parts of 3 and 6) called out:

1. **Finding 1** (delete `bedrock_pricing.rs`) — fully isolated, mechanical.
2. **Finding 3, step 1** (delete dead `tool_calling_rules()`) — zero risk,
   do it immediately regardless of anything else.
3. **Finding 9** (decide agents.rs's fate) — resolve this before finishing
   findings 3/6, since it changes their scope.
4. **Finding 3, steps 2-3** (retire the second tool catalog, fix the MCP
   stale-name bug) — now that 9 is resolved.
5. **Finding 4** (tool_selector enrichment → JSON) and **finding 5**
   (per-param error hints) — independent of each other and of everything
   above, can run in parallel with 2/3/6.
6. **Finding 2** (extract Bedrock's dialect parsing to a shared module) —
   pure code move, do whenever convenient.
7. **Finding 6** (consolidate system-prompt fragments) — do last among the
   prompt-affecting changes, since it depends on 9's outcome and its audit
   half needs a `Regression.md`-style before/after check, not just a
   compile check.
8. **Finding 7** (dispatch match consistency net) — independent, do
   whenever; the consistency test is worth adding even if the alias cleanup
   itself is deferred.
9. **Finding 8** (Mock provider simplification) — flagged medium-risk
   because it removes a GUI-reachable path; confirm scope with the user
   before deleting `MockPromptWindow.tsx` outright, then implement.
