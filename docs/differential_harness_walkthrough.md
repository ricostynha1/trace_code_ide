# One case, end to end: `REQ-CHECKOUT.total`

Every claim below is quoted from a file in `example/`. The one thing this
machine could not run is `lake build` (no Lean toolchain on this host); the
Python side transcripts are real, and `make e2e` runs both sides for real in the
container.

---

## The four files

| File | Role | How the link is known |
|---|---|---|
| `example/product/checkout.md` | the requirement | frontmatter `id: REQ-CHECKOUT`, clause `total` |
| `example/formal/Checkout.lean` | the executable model | `/-- @models REQ-CHECKOUT.total -/` on `price` |
| `example/engine/pricing.py` | the implementation | `# @implements REQ-CHECKOUT.total` on `price` |
| `example/.tracelean/drt.json` | the binding | `"op": "REQ-CHECKOUT.total"` |

No `src/` rule, no filename convention, no registry. Move any of these files
anywhere and the links move with them, because the link *is* the comment. And no
`harness/`: there is no adapter file, because TraceLean calls `pricing.price`
itself.

### 1. The requirement — `example/product/checkout.md`

```yaml
---
id: REQ-CHECKOUT
title: Checkout pricing
decomposition: complete
status: approved
clauses:
  total: the amount charged is the subtotal, minus the discount, plus shipping
---
```

### 2. The model — `example/formal/Checkout.lean`

Written from `product/*.md`, never from the code. If it were transliterated from
`pricing.py`, differential testing would compare the code against itself and
agree about the bugs.

```lean
structure Order where
  subtotalCents : Nat
  remote        : Bool
  deriving Repr, FromJson, ToJson

structure Priced where
  discountCents : Nat
  shippingCents : Nat
  totalCents    : Nat
  deriving Repr, FromJson, ToJson

/-- @models REQ-CHECKOUT.total -/
def price (o : Order) : Priced :=
  let discount := discountCents o.subtotalCents
  let afterDiscount := o.subtotalCents - discount
  let shipping := shippingCents afterDiscount o.remote
  { discountCents := discount
    shippingCents := shipping
    totalCents    := afterDiscount + shipping }
```

`deriving ToJson` on `Priced` is what fixes the wire format: Lean emits
`{"discountCents":…,"shippingCents":…,"totalCents":…}`. The adapter must return
exactly those keys.

### 3. The implementation — `example/engine/pricing.py`

```python
# @implements REQ-CHECKOUT.total
def price(subtotal_cents: int, remote: bool) -> dict:
    discount = discount_cents(subtotal_cents)
    after_discount = subtotal_cents - discount
    shipping = shipping_cents(after_discount, remote)
    return {
        "discountCents": discount,
        "shippingCents": shipping,
        "totalCents": after_discount + shipping,
    }
```

Note the signature disagreement that nothing needs to reconcile at the type
level: Lean takes one `Order`, Python takes two keyword arguments. That is the
adapter's job, below.

## What TraceLean generates

### The schema — inferred from the *model's* signature

`drt/infer.rs` reads `price (o : Order)`, sees a single structure argument, and
flattens `Order` into a struct schema. `drt/config.rs` writes it to
`example/.tracelean/drt.json`:

```json
{
  "req_id": "REQ-CHECKOUT",
  "clause": "total",
  "op": "REQ-CHECKOUT.total",
  "model":          { "cmd": [".tracelean/drt/.lake/build/bin/drtRunner"] },
  "implementation": {
    "language": "python",
    "entry": "engine/pricing.py::price",
    "params": { "subtotalCents": "subtotal_cents" }
  },
  "input": {
    "type": "struct",
    "fields": {
      "remote":        { "type": "bool" },
      "subtotalCents": { "type": "nat", "max": null,
                         "edges": [0,1,9,10,11,14,15,16,99,100,101,399,400,401,
                                   598,599,600,4999,5000,5001,9999,10000,10001,
                                   19999,20000,20001] }
    }
  },
  "coverage_floor": { "kind": "all-input-constructors" }
}
```

Those 26 `edges` are not hand-written. `infer::boundaries()` scanned
`Checkout.lean` for numeric literals — `20000 15 100 5000 10 0 10000 599 400` —
and emitted each ±1. Section "Why the edges matter" below shows what the run is
worth without them.

### The Lean runner — `example/.tracelean/drt/`

Generated by `drt/lean_runner.rs`, two files, neither hand-written:

`lakefile.lean`
```lean
package drt where
require «checkout-model» from "../../formal"
lean_lib DrtModel where
@[default_target]
lean_exe drtRunner where
  root := `DrtModel
```

The `require` name is `«checkout-model»` — the name `formal/lakefile.toml`
*declares*, not the directory name. Requiring it as `formal` makes Lake 4.12
**delete** `example/formal/`, which is why `check_requires()` refuses to run
`lake build` on a mismatch.

`DrtModel.lean` (excerpt — the dispatch for this clause, plus the loop):
```lean
import Checkout
open Lean
open Checkout

structure Case where
  case : Nat
  op : String
  input : Json
  deriving FromJson, ToJson

def handle (c : Case) : Except String Json :=
  match c.op with
  | "REQ-CHECKOUT.total" =>
    match fromJson? (α := Order) c.input with
    | .error e => .error s!"input: {e}"
    | .ok o =>
    .ok (toJson (Checkout.price o))
  | "REQ-DISCOUNT.tiers" =>
    match c.input.getObjValAs? _ "subtotal" with
    …

partial def loop (stdin stdout) : IO Unit := do
  let line ← stdin.getLine
  …
  stdout.putStrLn reply.compress
  -- Block-buffered pipe: without this flush the comparator waits forever.
  stdout.flush
  loop stdin stdout
```

`fromJson? (α := Order)` is the single-structure-argument case: the input object
is decoded whole. The other five bindings take scalars, so they pull named
fields with `getObjValAs?`. `open Checkout` is emitted because the model's
declarations live in `namespace Checkout`; without it, `Order` and `price` are
unknown identifiers.

`lake build` in that directory produces `.lake/build/bin/drtRunner` — the `cmd`
in `drt.json`.

### The implementation side — no file at all

The binding says which function to call and how to spell its arguments; the
runner shipped inside TraceLean (`core/src/drt/runners/python_runner.py`, written
into `.tracelean/drt/tracelean_drt_runner.py` when a run starts) does the rest:

```python
entry = Entry(root, binding)          # imports engine/pricing.py by path
kwargs = {params.get(k, k): v for k, v in payload.items()}
result = entry.function(**kwargs)     # pricing.price(subtotal_cents=…, remote=…)
```

Three things that used to be a per-binding file's job, now done once:

1. **Rename.** The model's field is `subtotalCents`; the implementation's
   parameter is `subtotal_cents`. `bind.rs` pairs them by declaration order,
   writes the pairing into the binding's `params`, and *says* it inferred it —
   so a guess is visible rather than silent.
2. **Shape.** The result must match the model's JSON field for field. Lean's
   `deriving ToJson` on `Priced` emits `{"discountCents":…,"shippingCents":…,
   "totalCents":…}` and `pricing.price` already returns exactly that. Dataclasses,
   named tuples and plain objects are unwrapped by the runner. Only a genuinely
   unmatchable return type needs the binding's `convert` hook.
3. **Survive.** An exception becomes `{"error": …}`, not a dead process.

There is no adapter form at all — not as a fallback either. Arbitrary code
between the implementation and the comparator could make a divergence disappear,
which is the one failure this system must not make easy.

This is the Cedar arrangement: one harness for the whole system, each entry point
described declaratively, rather than a generated protocol implementation per
property.

## The run

`drt::run` spawns both commands once and keeps them alive. Real transcript of
the implementation side (the model side computes the same arithmetic from
`Checkout.lean`):

```console
$ cd example
$ printf '%s\n' \
  '{"case":1,"op":"REQ-CHECKOUT.total","input":{"subtotalCents":9999,"remote":false}}' \
  '{"case":2,"op":"REQ-CHECKOUT.total","input":{"subtotalCents":11110,"remote":false}}' \
  '{"case":3,"op":"REQ-CHECKOUT.total","input":{"subtotalCents":20000,"remote":true}}' \
  | python3 .tracelean/drt/tracelean_drt_runner.py \
      --root . --bindings .tracelean/drt/bindings.python.json
{"case": 1, "output": {"discountCents": 999,  "shippingCents": 599, "totalCents": 9599}}
{"case": 2, "output": {"discountCents": 1111, "shippingCents": 599, "totalCents": 10598}}
{"case": 3, "output": {"discountCents": 3000, "shippingCents": 400, "totalCents": 17400}}
```

Case 2, step by step, on both sides:

| | model (`Checkout.price`) | implementation (`pricing.price`) |
|---|---|---|
| input | `{subtotalCents := 11110, remote := false}` | `subtotal_cents=11110, remote=False` |
| discount | `11110 * 10 / 100 = 1111` | `11110 * 10 // 100 = 1111` |
| after discount | `11110 - 1111 = 9999` | `9999` |
| shipping | `9999 < 10000` → `599 + 0` | `599` |
| total | `9999 + 599 = 10598` | `10598` |
| reply | `{"case":2,"output":{…,"totalCents":10598}}` | identical |

`replies_agree` compares the two JSON values structurally. Equal → next case.

## What a divergence looks like

The bug the model's own docstring predicts: pass the **pre-discount** subtotal to
shipping. Injected into a copy of `price` and run over the same inputs:

```console
9999  agree
11110 DIVERGE model={'discountCents':1111,'shippingCents':599,'totalCents':10598}
                impl={'discountCents':1111,'shippingCents':0,  'totalCents':9999}
20000 agree
5000  agree
99999 agree
```

This is the shape of bug that matters. The two versions disagree only when the
subtotal is above the free-shipping threshold but the *discounted* subtotal is
below it — `10000 ≤ subtotal ≤ 11111`, about **1100 values out of 4 billion**. A
handful of example-based tests miss it. So does uniform random `Nat`.

What happens next in `drt::run`:

1. **Shrink.** `gen::shrink` simplifies the failing input while the disagreement
   survives, so the report shows a minimal witness rather than the random value
   that happened to hit the band.
2. **Triage.** The divergence is recorded `Untriaged` and a person picks
   `ImplBug | ModelBug | AdapterBug`. The model is not privileged: it was written
   from prose by a human or an LLM and is as capable of being wrong as the code.
3. **Seed.** The failing input is appended to `example/.tracelean/drt/seeds/` and
   replayed first on every later run, so a fixed bug stays fixed.

### Why the edges matter

`subtotalCents` is an unbounded `Nat`, so a uniform draw lands somewhere in the
32-bit range. The probability of landing in that 1100-wide band by chance is
about 1 in 4 million; 2000 random cases would report "no divergences" and mean
nothing. The `edges` list contains `9999, 10000, 10001` — two of which sit
inside the band — so the bug is found on the first run. Measured by injecting
exactly this mutation: **0 divergences without edges, 32 of 2000 with them.**

## What the green run earns

```rust
pub fn earns_l3(&self) -> bool {
    self.divergences.is_empty() && self.coverage_floor_met && self.cases_run > 0
}
```

`coverage_floor` for this binding is `all-input-constructors`: every declared
input constructor exercised, and at least one output variant observed. A case
count on its own is theatre — a million cases down one branch establish nothing.

Clean run ⇒ **L3**, not L4. L4 is a machine-checked proof about the model
(`example/formal/CheckoutProofs.lean`, role `@proves`). Differential testing
buys falsification: evidence that the bug is not in the region sampled, never a
guarantee that there is none. The panel shows the chain — `req↔model` from the
judge, `model↔impl` from this run — and aggregates by the **minimum**, so an
L3 differential result under an unjudged model still reads as the weaker link.
