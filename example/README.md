# Checkout pricing — the TraceLean example project

A deliberately small project that exercises every part of TraceLean's
traceability design, including the parts that are supposed to look *unfinished*.
Open this directory as a project and press `Ctrl+Space` `t` to see it.

The domain is checkout pricing: a cart subtotal becomes a discount, a shipping
charge and a total. Everything is integer cents, pure and total, which is what
makes it cheap to model in Lean and cheap to test differentially.

---

## What this demonstrates, in one paragraph

A requirement written in English is formalized as an **executable Lean model**,
which is bound to the **implementation** by **differential testing** — running
both over the same random inputs and comparing answers. The implementation can
be in any language, because the bond is behavioural rather than syntactic. Every
link is a **comment annotation** in ordinary source, so no directory layout, no
filename rule and no registry file is imposed on the project.

---

## Layout — note that none of it matters

```
product/     the requirements (markdown with frontmatter)
formal/      the Lean model and its proofs
engine/      the Python implementation, including one deliberate defect
service/     the Rust implementation
checks/      tests, in both languages
```

There is no `harness/` either. The differential-testing harness is TraceLean's
code, not this project's: `.tracelean/drt.json` names the function each model
declaration corresponds to, and the runner shipped with TraceLean imports it and
calls it.

There is no `reqs/`, no `specs/`, no `src/`, no `tests/unit/`. Those names used
to *be* the traceability: a spec was linked to a requirement because the files
shared a stem. That is gone. Rename any directory here, move any file, and every
link survives, because a link exists only where somebody wrote one down.

## The five roles

| Role | Means | Here |
|---|---|---|
| `@models` | this Lean definition formalizes that clause | `formal/Checkout.lean` |
| `@implements` | this code realizes that clause | `engine/pricing.py`, `service/receipt.rs` |
| `@tests` | this test exercises that clause | `checks/pricing_checks.py`, `checks/receipt_checks.rs` |
| `@drt` | this adapter binds the model to the implementation | unused — bindings live in `.tracelean/drt.json`; see the note below |
| `@proves` | this Lean theorem discharges a property of the model | `formal/CheckoutProofs.lean` |
| `@pins` | this Lean theorem shows those properties *determine* the model | `formal/Strength.lean` |

`@pins` is the answer to "how much does that proof actually rule out". A theorem
can hold of many different functions: `discountCents s ≤ s` is satisfied by the
constant-zero discount, so proving it constrains the model far less than it
looks. `formal/Strength.lean` is generated by TraceLean — one obligation per
modelled declaration, arriving as `sorry` — and `shippingCents_pinned` is proved,
which is why `flat_below_threshold` and `remote_below_threshold` exist: the
obligation showed the original two theorems said nothing below 10,000 cents.
`discountCents_pinned` is still open, and it is *false* as stated, which is the
more useful answer.

`@drt` is a historical role. Differential testing used to need a hand-written
adapter per binding, and the annotation is what marked one. There are no
adapters any more — a binding in `.tracelean/drt.json` names the function and
TraceLean's own runner calls it — so nothing in this project carries the role.

Two qualifiers modify a claim rather than making one:

- `@partial reason="…"` — `engine/pricing.py`, on the remote-area surcharge. The
  code recognises a hard-coded postcode list rather than the carrier's table, so
  the clause is capped: it can never count as fully backed.
- `@exempt … reason="…" by=…` — `service/receipt.rs`, on the audit-log clause.
  Writing to a log is a side effect and the model is pure. An exemption stays in
  the denominator and carries a name, so it reads as a decision rather than as a
  clause that quietly disappeared.

## The things that are wrong on purpose

A demo where everything is green teaches nothing, because the interesting
question is what the tool does when a project is *normal*. Four gaps are built
in, and each one is a different lesson:

1. **`REQ-DISCOUNT.coupon` has no implementation at all.** No annotation claims
   it, because writing an annotation for code that does not exist is the one
   thing this system must never make easy. The checker reports it `Unmodeled`,
   and `REQ-DISCOUNT` sits at 33% coverage rather than pretending.

2. **`REQ-RECEIPT` is `decomposition: open`.** It says more children may exist
   and have not been written down. Every percentage computed over it renders as
   a lower bound — `≥ 44%` on the parent, not `44%` — and it can never show as
   finished. This is the denominator problem stated honestly instead of hidden.

3. **`REQ-RECEIPT.lines` has no model.** Not everything is worth formalizing; the
   point is that the tool says so rather than counting the clause as done.

4. **`REQ-DISCOUNT` sits at `L1` even though two of its three clauses are at
   `L3`.** Assurance aggregates by the weakest link, never by the mean: the
   unimplemented `coupon` clause sets the level for the whole requirement. A
   requirement is as trustworthy as its worst part, and averaging is how a
   dashboard comes to report a number nobody should act on.

What the project reports today:

| Requirement | Coverage | Assurance | Why |
|---|---|---|---|
| `REQ-CHECKOUT` | 100% | `L3` | modelled, implemented, differentially tested |
| `REQ-SHIPPING` | 83% | `L3` | all three clauses bound and passing |
| `REQ-DISCOUNT` | 67% | `L1` | `coupon` is unimplemented |
| `REQ-RECEIPT` | `≥ 50%` | `L1` | `decomposition: open`, so every figure is a bound |

## Running the pieces

**The tests** (no dependencies):

```sh
python3 -m unittest discover -s checks -p '*_checks.py'
```

**The implementation side of the protocol**, by hand, after a run has written
the runner into `.tracelean/drt/`:

```sh
echo '{"case":1,"op":"REQ-CHECKOUT.total","input":{"subtotalCents":10500,"remote":false}}' \
  | python3 .tracelean/drt/tracelean_drt_runner.py \
      --root . --bindings .tracelean/drt/bindings.python.json
# {"case": 1, "output": {"discountCents": 1050, "shippingCents": 599, "totalCents": 10049}}
```

One runner serves every binding and dispatches on `op` — `REQ-CHECKOUT.total`,
not `default` — exactly as the generated Lean runner does on the other side. An
op shared between two bindings would mean one of them was silently answered by
the other's model.

Nothing in the six bindings is written by hand except the `params` line that
says the model spells an argument `subtotalCents` where Python spells it
`subtotal_cents`.

**A full differential run** additionally needs a Lean toolchain. TraceLean
generates and builds the model-side runner into `.tracelean/drt/` — one module
covering every binding, derived from the same `@models` links the checker reads.
`.tracelean/drt.json` already points at the binary it produces. Without a
toolchain the run reports "no model runner" rather than quietly passing — the
same rule the judge follows.

Six of the seven bindings agree over 2000 random cases each. The seventh,
`REQ-DISCOUNT.cap`, does not — and that is the point of it. The model applies the
cap the requirement asks for; `engine/pricing.py` defines the constant, names the
function after it, and never uses it. Nothing about either file reads as wrong,
every test in `checks/` passes, and the differential run reports the
disagreement on its first pass with a shrunk witness: subtotal 33,351, model
5000, implementation 5002.

An example where everything agrees cannot make the argument for having an
executable model. This one can.

**That the harness can actually fail** is not something you have to take on
trust here: `REQ-DISCOUNT.cap` fails on every run, and its witness is saved to
`.tracelean/drt/seeds/` so it is replayed first forever after. Any other
mutation behaves the same way — change `>=` to `>` at the 20,000-cent threshold
and `REQ-DISCOUNT.tiers` reports 32 divergences in 2000 cases.

That it finds these boundaries at all is not luck. The input schema TraceLean infers
carries the model's own numeric literals as generation edges: an unbounded `Nat`
sampled uniformly is above 20,000 in essentially every case, so without them the
same mutation survives 2000 cases untouched — and the coverage floor still
reports "met".

## The bug this example is shaped around

`REQ-SHIPPING` says free shipping is decided on the subtotal **after** the
discount. An implementation that checks the pre-discount subtotal agrees with the
model on almost every order and disagrees only near the boundary: 10,500 cents
discounts by 1,050 to 9,450, which is *below* the free-shipping line.

`checks/pricing_checks.py` pins that one case, and
`formal/Checkout.lean` makes the ordering explicit in the model. Differential
testing finds the whole family of them without anyone having thought of the
example first — which is the argument for having a model at all.

## Gotchas worth knowing before you write annotations

- **Annotations must live in comments.** A docstring is a string literal, not a
  comment, and the scanner reads tree-sitter comment nodes — which is why every
  annotation in `engine/pricing.py` sits in a `#` comment above its function
  rather than in the docstring inside it.
- **Writing an annotation's literal spelling in prose creates a real
  annotation.** The checker then reports an unknown role or a qualifier with
  nothing to qualify, which is the correct reaction — it cannot distinguish
  "I am documenting this syntax" from "I meant it". Refer to roles by name in
  prose, the way this file's table does.
- **A qualifier attaches to the annotation above it**, so keep
  `@partial`/`@exempt` directly under the claim they modify.
- **`decomposition: complete` is a claim you are making**, not a formality. It is
  what licenses TraceLean to print an exact percentage.
