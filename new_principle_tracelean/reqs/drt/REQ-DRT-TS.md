# TypeScript conformance runner

The web frontend is a second implementation of the functions that read a buffer:
it splits the text into lines and it works out what can be done at a position,
because that is what drawing is. A second implementation is exactly the thing
this project's method exists to check, and checking it needs a runner.

The protocol already allows it. A runner is a process reading line-delimited
JSON, so which language it is written in is a detail of how it is generated —
`Binding.implementation` carries a `language` and the list is closed at the two
that have generators.

`runs_the_shipped_source` is what makes this cheaper than the Rust side. Node
strips the types and runs the file, so there is no build output that could
differ from the source the browser loads. The cost is the other side of the same
coin: a binding that does not fit the function is a runtime error rather than a
compile error, which is why `failure_is_an_answer` is a clause — the mismatch
must be reported as this case's error, with the name of what did not fit, and
must not be mistaken for a divergence about values.

One consequence is worth stating plainly: **the TypeScript carries no
annotations.** TraceLean has no TypeScript grammar, so it cannot say which
declaration a claim in one of those files is about, and
[ADR-0008](../../docs/decisions/ADR-0008-lean-grammar-limits.md) rejects
recovering that by reading text. So the claims about the TypeScript are made
where they can be placed and checked — in the binding file, which names
`web/src/view.ts::plainText` and its neighbours, and in the suites that drive
them. The files themselves say in prose what they realise, and say why the
claim is not in them.

`second_implementation_same_oracle` is the one that matters most. Comparing the
TypeScript against the Rust would be comparing two implementations, and two
implementations agree perfectly when both are wrong. Both are compared against
the Lean model, which is the only thing either of them is trying to be.
